# KnowFlow RAG 项目总述 —— 面试复习

> 简历描述：基于 Spring Boot 3 构建企业级 RAG 智能问答系统。用户问题经对话记忆加载与 Query Rewrite 改写拆分为子问题，通过三级意图树 + LLM 分类路由至知识库检索、MCP 工具调用或系统直答，置信度不足时触发歧义引导。KB 路径采用意图定向、全局向量、关键词多通道并行召回，经去重、RRF 融合、Rerank 精排；MCP 路径由 LLM 提取参数调用远端服务，两路并行后统一组装 Prompt 流式生成回答。搭建自建指标与 RAGAS 双层评测体系，意图 Top-1 准确率 ≥ 92%、Hit@5 ≥ 90%、Faithfulness ≥ 0.90。

---

## 一、项目背景：为什么做这个系统

### 业务痛点

企业内部知识分散在各种文档（MD/PDF/Word/PPT/Excel）和业务系统（销售数据、工单系统等）中。员工遇到问题时的现状：

- **知识查找低效**：要在多个系统之间翻找，不知道该看哪个系统、哪个文档
- **传统搜索局限**：关键词搜索无法理解语义（搜"怎么请假"找不到"休假制度"）
- **FAQ 机器人覆盖有限**：只能回答预设问题，稍微换个说法就答不上来
- **实时数据查不到**：知识库是静态文档，但业务问题经常涉及实时数据（"本季度华东销售排名"）

### 系统定位

KnowFlow RAG 要解决的核心问题是：**让员工用自然语言提问，系统自动判断该从哪里找答案——从知识库检索文档，还是调用业务系统接口获取实时数据——然后基于检索到的证据生成准确回答，而不是靠 LLM 自己编。**

### 面试话术参考

> "这个项目的背景是企业内部知识分散在各种文档和业务系统中，员工遇到问题要在多个系统之间翻找，效率很低。传统的关键词搜索无法理解语义，FAQ 机器人只能回答预设问题。我们做的这个系统，核心是让员工用自然语言提问，系统自动判断该从知识库检索文档、还是调用业务系统 API 获取实时数据，然后基于检索到的证据来生成回答——是有据可依的回答，不是让大模型自己编。"

## 三、系统架构

### 模块分层

```
前端 (React + TypeScript)
  │ SSE 流式
  ▼
bootstrap/     主应用（363 个 Java 文件，全部业务逻辑）
  │
  ├── infra-ai/    AI 基础设施层（LLM/Embedding/Rerank 客户端抽象 + 三态熔断路由）
  │
  ├── framework/   通用基础设施（缓存、上下文、DTO、异常、MQ、分布式 ID、Trace）
  │
  └── mcp-server/  独立 MCP Server 应用（暴露工具 API，如销售数据查询）
```

### 分层设计原则

- **infra-ai** 屏蔽模型供应商差异 → 换供应商不改业务代码
- **framework** 提供通用能力 → 换业务不动基础设施
- **bootstrap** 专注业务逻辑 → 所有 RAG 链路、意图识别、检索、MCP 都在这一层
- **mcp-server** 独立部署 → 工具服务与主应用解耦

### infra-ai 层的模型路由

```
LLMService (Facade)
  └── RoutingLLMService (路由)
       ├── SiliconFlowChatClient    (OpenAI 兼容)
       ├── OllamaChatClient         (本地 Ollama)
       ├── BaiLianChatClient        (阿里百炼)
       └── AIHubMixChatClient       (AIHubMix)
```

所有客户端通过 `ModelRoutingExecutor` + `ModelSelector` + `ModelHealthStore` 进行**健康感知的路由选择**，采用 CLOSED/OPEN/HALF_OPEN 三态熔断器：失败次数达阈值自动熔断（OPEN），冷却期后半开探测（HALF_OPEN），探测成功恢复（CLOSED）。配合优先级降级链，一个模型挂了自动切到下一个，业务层无感知。

### bootstrap 核心包结构

```
rag/
├── core/
│   ├── intent/       意图识别（IntentResolver、DefaultIntentClassifier、IntentTreeCacheManager）
│   ├── rewrite/      查询改写（QueryRewriteService、同义词标准化）
│   ├── retrieve/     检索引擎（RetrievalEngine、MultiChannelRetrievalEngine）
│   │   ├── channel/  检索通道（IntentDirected、VectorGlobal、Keyword）
│   │   └── postprocessor/  后处理器（Dedup、RRF Fusion、Rerank）
│   ├── guidance/     歧义引导（IntentGuidanceService）
│   ├── prompt/       Prompt 组装（RAGPromptService、ContextFormatter、模板加载）
│   ├── mcp/          MCP 集成（参数提取、工具注册、工具执行）
│   ├── memory/       对话记忆（摘要、压缩、持久化）
│   └── vector/       向量存储（Milvus、PgVector 两种实现）
├── service/
│   └── pipeline/     StreamChatPipeline（8 阶段管道编排）
├── eval/             评测旁路接口
└── trace/            可观测性（AOP 链路追踪）
```

## 四、核心对话流程（StreamChatPipeline）

管道共 **8 个阶段、3 个短路分支**，入口为 `StreamChatPipeline.execute()`：

```
用户提问
  │
  ▼
Stage 1: loadMemory()           加载对话历史 + 摘要，追加当前消息
  │
Stage 2: rewriteQuery()         同义词标准化 + LLM 改写 + 子问题拆分
  │                              （LLM 失败时 fallback 标点规则拆分）
  │
Stage 3: resolveIntents()       对每个子问题并行 LLM 意图分类
  │                              score < 0.35 过滤，每子问题 top-3，全局限制 3
  │
  ├── Stage 4: handleGuidance()      歧义引导检测
  │   └── [短路1] 返回引导语让用户选择（如"您问的是 OA 的数据安全还是保险的？"）
  │
  ├── Stage 5: handleSystemOnly()    系统对话检测（打招呼、自我介绍）
  │   └── [短路2] LLM 直接回复，不走检索
  │
Stage 6: retrieve()             多路检索（KB + MCP 并行）
  │   KB: 意图定向 + 全局向量 + 关键词 → 去重 → RRF 融合 → Rerank
  │   MCP: LLM 参数提取 → 远程工具调用 → 结果格式化
  │
  ├── Stage 7: handleEmptyRetrieval()
  │   └── [短路3] 返回"未检索到相关文档"兜底提示
  │
Stage 8: streamRagResponse()    Prompt 组装 + 流式 LLM 生成
  │   场景选择: KB_ONLY (temp=0) / MCP_ONLY (temp=0.3) / MIXED
  │   消息结构: [System Prompt] + [对话历史] + [证据 + 问题]
  └── SSE 流式推送给前端
```

### 面试话术参考

> "整个对话链路是一个 8 阶段的流水线，有 3 个短路分支。用户问题进来后，先加载对话记忆和历史摘要，然后做查询改写和子问题拆分——比如用户问了一个复合问题，就拆成多个独立子问题分别处理。接着对每个子问题并行做意图识别，通过三级意图树 + LLM 分类，判断每个子问题该走知识库检索、MCP 工具调用、还是系统直答。如果发现歧义就短路返回引导语让用户澄清。确定路径后，KB 意图走多通道并行检索，MCP 意图走参数提取 + 工具调用，两条路径并行执行。最后把检索到的证据和问题组装成 Prompt，流式调用 LLM 生成回答。"

## 五、设计模式与工程实践

| 设计模式 | 应用场景 | 解决的问题 |
|---|---|---|
| 策略模式 | SearchChannel、PostProcessor、McpToolExecutor | 检索通道、后处理器、MCP 工具可插拔替换 |
| 工厂模式 | IntentTreeFactory、StreamCallbackFactory | 复杂对象创建逻辑集中管理 |
| 注册表模式 | McpToolRegistry、IntentNodeRegistry | 组件自动发现与注册，新增工具零配置 |
| 模板方法 | AbstractParallelRetriever、IngestionNode | 统一执行框架，子类只关注核心逻辑 |
| 装饰器模式 | ProbeBufferingCallback | 不修改原回调前提下增加首包探测能力 |
| 责任链模式 | 后处理器链、模型降级链 | 多步骤按顺序串联，灵活组合 |
| 观察者模式 | StreamCallback | 流式事件的异步通知 |
| AOP | @RagTraceNode、@ChatRateLimit | 链路追踪和限流与业务代码解耦 |

## 六、生产级特性

| 特性 | 实现方式 |
|---|---|
| **限流** | 全局并发限制 + 用户级限流（ChatQueueLimiter），防止模型调用被打爆 |
| **熔断** | 三态熔断器（CLOSED/OPEN/HALF_OPEN）+ 优先级降级链，模型故障自动切换 |
| **可观测性** | `@RagTraceNode` AOP 注解，每个环节的耗时、输入输出、异常都有记录 |
| **流式输出** | SSE 实时推送 + 首包探测（ProbeBufferingCallback），模型切换时用户无感知 |
| **会话管理** | 消息数 > 8 触发摘要压缩、TTL 过期清理，防 OOM 和 Token 爆炸 |
| **异常隔离** | 每层并行都用独立线程池 + 独立 try-catch，单点故障不扩散 |

## 八、面试高频问题

### Q1：这个项目和直接用 LangChain / LlamaIndex 有什么区别？

> "LangChain/LlamaIndex 是通用框架，适合快速搭原型，但企业场景有几个特殊需求它们不好满足：一是意图路由需要业务运营人员在后台直接配置和调整，不是靠模型自己判断；二是多模型供应商的熔断降级、限流这些生产级特性需要自己做；三是评测体系需要和业务指标对齐，通用框架只提供基础能力。所以我们选择基于 Spring Boot 自建，核心链路全部可控可观测，但设计上借鉴了它们的思路——比如检索通道的策略模式、后处理器的责任链模式。"

### Q2：为什么选 Spring Boot 3 而不是 Python 框架？

> "两个原因：一是团队技术栈以 Java 为主，Spring Boot 生态成熟，和企业内部的认证、消息队列、数据库等基础设施无缝集成；二是 Java 的并发模型（CompletableFuture + 线程池）在多通道并行检索场景下比 Python 的 asyncio 更好控制——我们有 5 个独立线程池、3 层并行嵌套，Java 的类型系统和并发原语让这种复杂的并行编排更可靠。评测部分用 Python 是因为 RAGAS 等学术评测工具的生态在 Python 侧更成熟。"

### Q3：系统的 QPS 能到多少？瓶颈在哪里？

> "RAG 系统的瓶颈不在传统意义的 QPS，而在 LLM 调用的延迟和并发限制。整个链路有 3-4 次 LLM 调用（改写、意图分类、参数提取、最终生成），每次几百毫秒到几秒。我们通过几个手段优化：一是子问题级和通道级并行，把串行等待变成并行；二是意图树 Redis 缓存（7 天 TTL），避免每次查数据库重建；三是 ChatQueueLimiter 做全局并发控制，防止超过模型供应商的 rate limit。首字延迟（TTFT）目标是 ≤ 6 秒。"

### Q4：为什么不用 Agent（如 ReAct）模式，而是固定管道？

> "Agent 模式的优势是灵活——模型自己决定下一步做什么，但缺点是不可预测、不可控、难以调优。企业场景对'稳定可控'的要求高于'智能自主'：业务方需要明确知道这个问题走了哪个知识库、调了哪个工具，出问题能快速定位。固定管道的每个阶段都有明确的输入输出、可配置的阈值、独立的日志和 trace，排查问题远比 Agent 的多轮循环容易。而且我们的场景不需要多步推理——一次意图识别 + 一次检索/工具调用就够了，没必要为此引入 Agent 的复杂性。"

### Q5：你在这个项目中负责什么？

> "我是这个项目的核心开发，负责了三个主要技术模块的设计和实现：一是树形意图识别和智能路由，从意图树的数据结构设计、LLM 分类 Prompt 调优、到歧义引导的三级判定策略；二是多通道混合检索引擎，包括三个检索通道的设计、RRF 融合算法的实现、后处理器链的架构；三是评测体系的搭建，包括 Java 侧的旁路接口、Python 侧的双层指标计算、回归对比机制。另外也参与了 infra-ai 层的模型路由和熔断降级的设计。"
