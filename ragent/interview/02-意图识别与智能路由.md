# 技术点一：树形意图识别与智能路由 —— 面试复习

> 简历描述：设计三级意图树 + LLM 分类混合方案，结合查询改写、子问题拆分与歧义判定，将用户问题精准路由至知识库、MCP 工具或系统直答链路，意图 Top-1 准确率 ≥ 92%

---

## 一、做什么

把用户的自然语言问题，精准路由到正确的下游处理路径：

| 路径 | 含义 | 示例 |
|---|---|---|
| **KB（知识库检索）** | 从向量数据库检索相关文档片段 | "招聘政策有哪些？" |
| **MCP（工具调用）** | 调用业务系统接口获取实时数据 | "华东地区本季度销售排名前5" |
| **SYSTEM（系统直答）** | LLM 直接回复，无需检索 | "你好"、"你是谁" |

这是整个 RAG 链路的"第一跳"——意图判断错了，后面检索和生成全部白做。

---

## 二、怎么实现的（核心技术）

### 2.1 三级意图树

意图用**树形结构**组织，存储在 MySQL `t_intent_node` 表，通过 Redis 缓存（7 天 TTL）。核心类：`IntentNode`、`IntentTreeCacheManager`、`IntentTreeFactory`。

```
DOMAIN（领域）
  └── CATEGORY（分类）
       └── TOPIC（主题）← 叶子节点，只有叶子节点参与 LLM 分类
```

具体示例：
```
集团信息化 (DOMAIN)
├── 人事 (CATEGORY)
│   ├── 招聘政策 (TOPIC, KB)  → collection: hr_recruitment, topK: 10
│   └── 薪酬福利 (TOPIC, KB)  → collection: hr_compensation
├── IT (CATEGORY)
│   └── 技术支持 (TOPIC, KB)  → collection: it_support, topK: 20
└── 财务 (CATEGORY)
    └── 发票信息 (TOPIC, KB)  → collection: finance_invoice
        → promptSnippet: "回答时注意区分增值税普通发票和专用发票"
        → promptTemplate: "你是一个财务发票助手..."

MCP 工具 (DOMAIN)
└── 销售数据 (TOPIC, MCP)  → mcpToolId: sales_data_query

系统交互 (DOMAIN)
├── 打招呼 (TOPIC, SYSTEM)
└── 关于机器人 (TOPIC, SYSTEM)
```

每个叶子节点携带的关键字段：

| 字段 | 作用 |
|---|---|
| `kind` (KB/MCP/SYSTEM) | 决定下游走哪条路径 |
| `collectionName` | KB 类型对应的 Milvus Collection |
| `mcpToolId` | MCP 类型对应的工具 ID |
| `topK` | 该意图的检索数量（覆盖全局默认值） |
| `examples` | 示例问法，帮助 LLM 判断 |
| `promptSnippet` | 业务规则片段，注入上下文 |
| `promptTemplate` | 意图专属完整 Prompt 模板 |
| `paramPromptTemplate` | MCP 参数提取的自定义 Prompt |

### 2.2 查询改写 + 子问题拆分

在意图识别前，先经过 `QueryRewriteService.rewriteWithSplit()` 做预处理。核心类：`MultiQuestionRewriteService`、`QueryTermMappingService`。

**Step 1 — 同义词/缩写标准化**

`QueryTermMappingService.normalize()`：把口语化表达映射到标准术语（如"请假" → "休假制度"），存储在数据库，管理后台可配置。

**Step 2 — LLM 改写 + 拆分**

用 `user-question-rewrite.st` 模板调用 LLM，做两件事：
- **改写**：结合对话历史补全指代（如"它的政策是什么" → "招聘的政策是什么"）
- **拆分**：复合问题拆成独立子问题（"招聘政策和本季度销售数据" → ["招聘政策有哪些？", "本季度销售数据是什么？"]）

**Step 3 — 降级兜底**

LLM 调用失败时，fallback 到标点符号规则拆分（按句号、问号、分号切分），保证链路不中断。

### 2.3 LLM 意图分类

核心类：`DefaultIntentClassifier.classifyTargets()`。

**一次性发送所有叶子节点给 LLM**：把所有叶子节点的 `id`、`fullPath`、`description`、`examples`、`kind` 生成为结构化文本，用 `intent-classifier.st` 模板包裹，要求 LLM 在这些 id 中选择并打分。

LLM 调用参数：`temperature=0.1, topP=0.3`（低温度保证分类稳定性）。

LLM 返回示例：
```json
[{"id":"node_001", "score":0.92, "reason":"用户明确询问招聘政策"}]
```

### 2.4 过滤 + 配额分配

核心类：`IntentResolver.resolve()`。

**子问题级过滤**：每个子问题通过 `intentClassifyExecutor` 线程池并行分类，然后：
- `score < 0.35` (INTENT_MIN_SCORE) 过滤掉
- 每个子问题最多保留 top-3 (MAX_INTENT_COUNT)

**全局配额限制 `capTotalIntents()`**：当多子问题的意图总数超过 3 时：
1. 每个子问题**至少保留 1 个最高分意图**（保底，`selectTopIntentPerSubQuestion()`）
2. 剩余配额按所有候选意图的**分数从高到低**分配（`selectAdditionalIntents()`）
3. 通过 `rebuildSubIntents()` 重建结果

### 2.5 歧义引导

核心类：`IntentGuidanceService.detectAmbiguity()`。

当单个子问题命中 2+ 个 KB 意图且分数接近时触发。例如用户问"数据安全"，同时命中"OA 系统 > 数据安全"(score=0.85)和"保险系统 > 数据安全"(score=0.82)。

**三级判定策略**：
```
ratio = 第二高分 / 最高分 = 0.82 / 0.85 = 0.965

ratio < 0.65              → 明确不歧义，直接走检索
0.65 ≤ ratio < 0.8        → 灰色地带，调 LLM 二次确认（guidance-ambiguity-check.st）
ratio ≥ 0.8               → 明确歧义，生成引导语让用户选择（guidance-prompt.st）
```

歧义引导是**短路分支**：直接返回引导文本，不走后续检索。

配置参数：
```yaml
rag.guidance:
  ambiguityScoreRatio: 0.8     # 歧义阈值
  ambiguityMargin: 0.15        # 灰色地带宽度 (0.8 - 0.15 = 0.65)
  maxOptions: 6                # 引导选项最多数量
```

### 2.6 意图分组

`IntentResolver.mergeIntentGroup()` 将识别结果分为两组，决定下游路径：

```java
IntentGroup {
    mcpIntents → MCP 工具调用路径
    kbIntents  → 多通道检索路径
}
```

同时决定 Prompt 场景：全 KB → `KB_ONLY`(temp=0) / 全 MCP → `MCP_ONLY`(temp=0.3) / 混合 → `MIXED`。

## 三、为什么这样做

### 为什么用树形结构而不是纯向量相似度路由？

**企业场景的核心需求是"可管理"**。业务运营人员需要在后台直接配置和调整分类——新增一个意图节点、绑定知识库、设置专属 Prompt 和 topK，这些结构化元数据（`collectionName`、`topK`、`promptSnippet`）是向量相似度路由承载不了的。树形结构对应企业的组织和业务分类心智模型，业务同学直接在管理后台操作，不需要理解向量检索原理。三级层次（DOMAIN/CATEGORY/TOPIC）也让权限管理、Prompt 复用有了自然的组织方式。

### 为什么一次性发所有叶子给 LLM，而不是逐层下钻分类？

逐层下钻（先分到 DOMAIN，再 CATEGORY，最后 TOPIC）需要 **3 次 LLM 调用**，延迟是一次性分类的 3 倍。更严重的是**错误累积**——上层分错会导致下层无法纠正。一次性分类让 LLM 看到全局上下文做更准确的判断，只需一次调用。当前叶子节点量级在几十到一两百，Prompt 长度可控。

### 为什么限制意图总数上限为 3？

不限制的话，多子问题 × 多意图会导致**检索通道数线性增长**，直接拖慢延迟，同时过多证据混入 Prompt 会**稀释上下文相关性**，反而降低生成质量。3 是在"检索覆盖度"和"延迟 + 上下文噪声"之间的经验权衡值。

### 为什么要"保底 + 按分配额"而不是简单全局截断？

简单全局截断（按分数排序取 top-3）可能导致某个子问题的**所有意图分数都偏低而被全部淘汰**，该子问题完全没有检索结果，答非所问。保底策略保证每个子问题至少有一个意图参与下游处理。

### 为什么歧义判定要分三档？

单一阈值在边界附近大量误判——ratio=0.79 和 0.81 实际歧义程度可能差不多，但被区别对待。三级判定：明确区域直接给结论（省 LLM 调用），灰色地带才调 LLM 二次确认，平衡了**准确性**和**成本/延迟**。

## 四、遇到的困难与解决方案

### 困难 1：意图分类准确率从 ~80% 到 ≥92% 的提升过程

**问题**：最初 Prompt 只给了叶子节点的 `name` 和 `description`，LLM 对相似意图区分不清（如"技术支持"和"系统介绍"经常混淆），整体准确率只有约 80%。

**分析过程**：通过评测体系的分层分析功能，发现准确率低集中在几个特定意图对上。查看 LLM 返回的 `reason` 字段，发现模型在缺少上下文时倾向于选择描述更宽泛的那个。

**解决方案**（三步优化）：
1. **增加 `examples` 字段**：每个意图节点配置 3-5 个示例问法（如"校招流程"、"社招政策"），让 LLM 有具体参考，而不是只靠抽象描述判断
2. **增加 `fullPath` 字段**：把完整路径（"集团信息化 > 人事 > 招聘政策"）发给 LLM，提供层次上下文，帮助区分同名但不同领域的意图
3. **调整 LLM 参数**：将 `temperature` 从 0.3 降到 0.1、`topP` 从 0.5 降到 0.3，减少随机性，让分类更稳定

**效果**：准确率从 ~80% 提升到 92%+，主要提升来自 examples 字段（贡献约 8 个百分点）。

### 困难 2：复合问题路由错误

**问题**：用户问"招聘政策和本季度销售数据"，如果不拆分，意图分类只会命中一个（通常是排在前面的 KB 意图），MCP 调用完全被忽略。

**分析**：LLM 在面对复合问题时，倾向于只识别出最显著的那个意图，因为 Prompt 要求它"选择最匹配的意图"。

**解决方案**：增加查询改写阶段做**子问题拆分**：
1. LLM 改写时同时拆分子问题（`user-question-rewrite.st` 模板指示 LLM 识别独立信息需求）
2. 每个子问题独立进行意图分类（通过 `intentClassifyExecutor` 线程池并行执行）
3. 通过 `IntentGroup.mergeIntentGroup()` 将所有子问题的意图按 KB/MCP 分组，两条路径并行执行

**降级保护**：LLM 改写失败时 fallback 到标点符号规则拆分，保证链路不中断。

### 困难 3：歧义场景答非所问

**问题**：用户问"数据安全相关规定"，系统中 OA 和保险两个业务域都有"数据安全"意图，两者分数非常接近（如 0.85 vs 0.82），系统随机选一个，50% 概率答错。

**分析**：问题的根源是**意图节点命名不唯一**——同一个名字在不同业务域有不同含义，LLM 无法判断用户到底问的是哪个。

**解决方案**：设计歧义引导机制，分三步：
1. **检测歧义**：计算 top-2 意图的分数比值（ratio = 第二高分 / 最高分）
2. **三级判定**：明确不歧义直接走、明确歧义直接引导、灰色地带调 LLM 二次确认
3. **短路返回**：歧义确认后生成引导语（"您是想了解 OA 系统还是保险系统的数据安全规定？"），直接返回给用户，不走检索

**关键设计**：三级判定而非单一阈值，避免了阈值附近大量误判的问题。同时引导选项数量限制为最多 6 个，防止选项过多用户反而更困惑。

### 困难 4：意图树缓存一致性

**问题**：意图树存储在 MySQL，通过 Redis 缓存（7 天 TTL）。管理员在后台修改意图节点后，缓存中的旧数据会导致分类使用过期的树结构。

**解决方案**：`IntentTreeCacheManager` 实现了**主动失效 + 被动过期**双重策略：
- **主动失效**：意图节点 CRUD 操作时，通过事件机制主动清除 Redis 缓存键 `ragent:intent:tree`
- **被动过期**：7 天 TTL 作为兜底，即使主动失效遗漏，缓存也会自然过期
- **重建时加载全量**：cache miss 时一次性加载所有节点、组装父子关系、填充 fullPath，避免多次查库

## 五、量化指标与优化过程

| 指标 | 优化前 | 优化后 | 提升手段 |
|---|---|---|---|
| Top-1 准确率 | ~80% | ≥ 92% | 增加 examples + fullPath + 低温度参数 |
| 复合问题命中率 | ~60% | ~90% | 子问题拆分 + 并行分类 |
| 歧义场景误答率 | ~50% | <5% | 三级歧义引导 |
| 意图分类延迟 | ~2s（逐层下钻 3 次调用） | ~800ms（一次调用） | 一次性全集分类 |

## 六、面试高频问题

### Q1：意图树如果叶子节点非常多（比如上千个），Prompt 会不会太长？

> "这是个好问题，目前我们的场景叶子节点在几十到一两百个量级，Prompt 长度可控。但如果扩展到上千个，确实需要优化。有几个思路：一是做**两阶段分类**——先用 embedding 相似度粗筛出 top-N 个候选叶子（比如前 30 个），再把这 30 个发给 LLM 做精排，这样 Prompt 长度恒定；二是在 DOMAIN 层先做一次快速分类缩小范围，再在子集内精分——虽然有两次调用，但每次 Prompt 都短；三是用 fine-tuned 的小模型做分类，完全不用发意图列表。具体选哪个取决于节点增长速度和延迟要求。"

### Q2：你的意图分类和 function calling / tool_use 有什么区别？为什么不直接用？

> "function calling 让模型在一次推理里同时决定'调哪个工具'和'传什么参数'，链路更短。但企业场景有两个短板：一是**工具选择不可管理**——无法像意图树一样做分层配置、置信度阈值、歧义引导，工具选择完全是模型黑盒，难以调优和追责；二是**参数提取和工具选择耦合**——无法针对某个工具单独定制提取逻辑。我们拆成两步后，工具选择复用了意图树的路由体系（可配置、可观测），参数提取可以为每个工具单独设计 Prompt。出问题时也能快速定位是'选错工具'还是'参数提错'。代价是牺牲了原生 tool_use 的多步推理能力，但我们的场景不需要多轮工具调用循环。"

### Q3：LLM 分类的稳定性怎么保证？同一个问题两次分类结果不一样怎么办？

> "三个手段：一是**低温度参数**（temperature=0.1, topP=0.3），大幅降低随机性；二是**结构化 Prompt**——明确要求 LLM 只在给定的 id 集合中选择，输出严格 JSON 格式，减少自由发挥空间；三是**分数阈值过滤**（score < 0.35 丢弃），即使分类有波动，低置信度的结果也会被过滤掉。实测中，相同问题重复分类的 top-1 意图一致率在 98% 以上。"

### Q4：如果用户的问题完全不属于任何已配置的意图怎么办？

> "这种情况下 LLM 会给所有意图打低分（通常都低于 0.35 的阈值），所有意图被过滤掉后，子问题的意图列表为空。这时会走两条路：如果全局检索通道是启用的（VectorGlobalSearchChannel），会做一次跨所有知识库的全量向量检索作为兜底；如果检索也没有结果，Stage 7 的 `handleEmptyRetrieval()` 会短路返回'未检索到与问题相关的文档内容'。不会出现系统沉默不回复的情况。"

### Q5：查询改写会不会改变用户的原始意思？

> "这是改写环节最大的风险。我们在 Prompt 中明确约束了 LLM：'改写的目标是补全指代和消除歧义，不要添加用户没有表达的信息'。同时改写结果和原始问题都会传递给下游——如果改写后意图识别的置信度反而降低了，系统会回退使用原始问题。改写质量也纳入了评测体系，通过 embedding 相似度检查改写前后的语义偏移。"

### Q6：你怎么评估意图识别的准确率是 92%？

> "通过评测体系中的 `intent_top1_accuracy` 指标。评估集中每条样本标注了 `intent_l2`（叶子节点 ID），录制时通过 `/rag/eval` 旁路接口拿到系统实际预测的 `intentLeafIds[0]`，逐条比对是否一致。评估集按难度（easy/medium/hard）和意图类别分层，可以看到哪些意图准确率高、哪些低——比如 easy 题 98%、hard 题可能只有 85%，整体加权 92%。分层分析能精准定位薄弱意图节点，针对性优化其 description 和 examples。"
